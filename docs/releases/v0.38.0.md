## Summary

Bilateral commerce goes live: positive-credit ledger semantics (0.0 start), bilateral netting cycle (reconcile/propose/accept/execute/confirm), chain-aware settlement, and the economy foundation for real money flows. Hardened by a 5-model adversary panel with 11 accepted findings fixed.

## Ledger Semantics Change

**Breaking:** New peers start at balance 0.0 (was `initial_credit`, typically 3.0).

- `balance < 0` = they owe us (they consumed more than they provided)
- `balance > 0` = we owe them (they provided more than they consumed)
- Effective balance = `balance + prepaid` (prepaid deposits count toward credit)
- Admission check uses `effective_balance - price < hard_limit` instead of `balance < min_balance`

Migration `v0_38_0.sql` adds: `prepaid`, `pub_tab`, `soft_limit`, `hard_limit`, `credit_limit` columns to ledger.

Balance migration (`run_v038_balance_migration`) shifts existing balances by `-default_soft_limit` to normalize to the new 0-start convention. Idempotent via `kv_meta` marker table.

## New Modules

### Chain Selector (`src/knarr/core/chain.py`)
Multi-chain support foundation. `select_chain()` resolves blockchain config from `knarr.toml`. Supports Solana devnet/mainnet with chain_id validation.

### Netting Policy (`src/knarr/commerce/netting_policy.py`)
Configurable netting thresholds. Default settlement threshold from config, per-peer overrides.

### Netting Query (`src/knarr/commerce/netting_query.py`)
API for querying netting state: raw book (all positions), node scope (single peer), felag scope (group), computed (with settle/skip action).

### Currency Conversion (`src/knarr/commerce/conversion.py`)
Credit-to-token conversion with configurable rate. Rounding control, minimum settlement amount.

## Netting Lifecycle

Five-phase bilateral netting:
1. **Reconcile** — compute net position between two peers
2. **Propose** — offer settlement at computed amount
3. **Accept** — counterparty agrees to proposed amount
4. **Execute** — on-chain settlement via Solana RPC
5. **Confirm** — settlement receipt with tx signature

Each phase validates `chain_id` against node config. Empty chain_id rejected (FIX-006).

- **FIX-006** [MEDIUM]: Chain_id validation — empty string bypass closed
- **FIX-007** [MEDIUM]: `get_or_create_ledger_entry` — fetches stored `prepaid`/`hard_limit`, not defaults
- **FIX-008** [MEDIUM]: NaN/Inf guard on `update_ledger_provider`/`consumer`
- **FIX-009** [MEDIUM]: NaN/negative guard on `update_prepaid`
- **Issue #18** [HIGH]: Self-call economy bypass — local skills skip admission gate entirely

## Bounty Support

Negative-price skills (bounties) flow correctly through bilateral ledger:
- Provider: `balance -= (-price)` = balance increases (we owe them)
- Consumer: `balance += (-price)` = balance decreases (they owe us)
- Bounties skip admission check (peer is earning, not spending)
